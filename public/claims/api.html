Claim Triage Desk

API

The same pipeline as the desk, as a versioned HTTP API a claims system can call. JSON in, verified facts out. Described in OpenAPI 3.1.

DeskMonitoringCode
A fictional demo. Do not send real personal or medical data. The API is open with rate limits; in production it would sit behind the insurer's API gateway and identity provider.

Endpoints

MethodPathWhat it does
POST/api/v1/extractExtract facts from a sample claim, or from up to 3 documents of your own: text, or up to 2 images or PDFs (1.5 MB each).
GET/api/v1/healthWhether live mode is on, the models, prompt version, file types and limits.
POST/api/v1/feedbackThe handler's decision next to the AI suggestion. Feeds the override rate.
GET/api/v1/metrics?days=14Daily counters for the monitoring page.
GET/api/openapi.jsonMachine-readable description of all of the above.

Try it

Extract a sample claim. Sample results are cached, so this costs nothing after the first run.


      

      

    


    

      
Your own documents

      
Text documents go in text. Scans, phone photos and PDFs go in file as base64. For a file, the response includes the model's full transcription, and every quote is checked against it.

      

    


    

      
Python

      
A small client with no dependencies is in examples/claimdesk_client.py. Its integration tests run on every commit against a local copy of the server with a mock model.

      

    


    

      
What comes back

      
    
        
  • facts: each with doc_id, kind, normalised value, the exact quote, its character span and a confidence. Only facts whose quote exists in the document are here.
    • 
        
  • rejected: what the model returned that failed a check (quote not found, impossible date, invalid ICD-10 code), with the reason. Shown to a person, never silently fixed.
    • 
        
  • injections: passages that try to instruct the system, flagged by pattern rules, the model, or both.
    • 
        
  • transcripts and translations: the model's reading of each scan, and an English version of documents not in Czech or English.
    • 
        
  • usage, costUsd, latencyMs, cached: for cost control and monitoring.
    • 
      

    


    

      
Errors and limits

      
    
        
  • 400 invalid input, with a code such as bad_file, too_many_files or doc_too_long.
    • 
        
  • 429 rate_limited after 8 own runs a day per IP, or budget when the daily model budget is used up.
    • 
        
  • 502 model_error with the upstream error type, never the key. Not cached, safe to retry.
    • 
        
  • 503 live_off when no model key is configured. Cached sample results are still served.
    • 
      

    


    

      
What production would add

      
    
        
  • Authentication through the API gateway (for example Azure API Management with Entra ID) instead of open access.
    • 
        
  • An EU-hosted model inside the insurer's cloud, because medical reports are special-category data under GDPR.
    • 
        
  • Asynchronous jobs for long PDFs, with a callback to the claims system.
    • 
        
  • Metrics in a real store with alerts, and the evaluation set re-run on every prompt or model change before release.
