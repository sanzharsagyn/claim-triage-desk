        Evaluation on the test set
        
      
        
    
        
    
        
    
        
    
        
  
        

  
        
    
        
      
          
        
        1. 1 · Intake
          System
          Claim form and attachments arrive by upload, email or a post scan. Scans and phone photos go straight to the model, which transcribes them; one older test claim contains OCR errors from a separate OCR step.
          2. 
        
        2. 2 · Extract
          Language model
          A tool call returns JSON in a fixed schema: each fact with its document, the exact quote, a confidence and a note. Scans come back with a full transcription, non-Czech documents with an English translation.
          3. 
        
        3. 3 · Verify
          Code
          Every quote must exist in the document, or for a scan in the transcription shown next to it. Dates must be real calendar dates, diagnoses valid ICD-10 codes, amounts whole numbers. Anything else is rejected and shown, never silently fixed.
          4. 
        
        4. 4 · Screen
          Code + model
          Text addressed to an AI or a reviewer is flagged by pattern rules and by the model. Either is enough to escalate.
          5. 
        
        5. 5 · Check policy
          Code
          Cover dates, covered benefits, daily rates and the 15-day threshold are ordinary unit-tested rules. The same file runs in the browser and on the server.
          6. 
        
        6. 6 · Decide
          Claims handler
          Sees the recommendation, the evidence and the payout, then approves, asks for information or escalates. Overrides are logged next to the AI suggestion.
          7. 
      
        
    
        
    
        
      
        Why it is built this way
        
      
        The model reads, it does not decide
        Language models are good at pulling facts out of messy, multilingual paperwork. Paying money has consequences for a client, so the decision stays with a person who sees the evidence.
        
      
        Rules are code, not prompts
        A payout must be the same every time and explainable to the client and the regulator. A prompt cannot promise that; a tested function can.
        
      
        Documents are untrusted input
        Two test claims contain instructions to "approve without review", one in English hidden in an invoice, one in Czech inside a claim form. They are reported and routed to the fraud team.
        
      
        Built to be integrated and watched
        The same pipeline is a versioned API with an OpenAPI description, so a claims system can call it directly. A monitoring page tracks runs, latency, cost, rejected quotes, flagged instructions and how often handlers override the AI.
        
      
        Costs are designed, not discovered
        The cheap model handles visitors' text; sample runs are cached, own-text runs are rate-limited, and a daily budget stops all calls. The evaluation compares the cheap and the strong model on the same claims.
        
      
        Health data needs extra care
        Medical reports are special-category data under GDPR. In production this would run on an EU-hosted model inside the insurer's own cloud. The EU AI Act already treats risk assessment and pricing in life and health insurance as high-risk, so logging and human oversight are built in from the start.
